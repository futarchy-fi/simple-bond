# Notification & email-liveness redesign — 2026-06-11

Owner ask (verbatim intent):
1. **Heartbeat send** — actually send a *real* email every ~6h.
2. **Green ⟺ proven send** — `bond_email` is green ONLY if a real-or-heartbeat
   email was actually accepted by the provider in the last ~8h. "Green" must
   imply "mail is flowing", not merely "a key is configured".
3. **No silent failure** — know the *index* of the last notification sent and
   whether the last notification went out within the last *X* blocks; a stalled
   notifier must be visible, never silent.
4. **Per-event notifications** — new bonds, new judges, new challenges show up on
   the Futarchy Status Bot (Telegram), not just status-component transitions.

This supersedes the old `bond_email` semantics ("degraded until a provider key is
configured"), which proved that a *configured* key still doesn't prove a *working*
pipeline.

---

## Current state (what's already true)

- **bond.futarchy.ai** — frontend live (Netlify, marker-checked), backend live on
  the GCP VM behind Caddy at `api.bond.futarchy.ai`, mainnet on SimpleBondV6.
- **Email** — `backend/mailer.mjs` is provider-agnostic (SMTP→nodemailer or
  Resend), returns a message-id on success, `null` on failure/disabled, never
  throws. **No provider credential is set**, so every send is an honest no-op.
- **Monitoring** — `status.futarchy.fi` has `bond_email` + `bond_frontend`
  components; the @azhermes bot (VM systemd timer, 15-min) alerts on any
  component transition and posts a silent 6-h heartbeat. `bond_email` is
  currently 🟡 *degraded* with "Delivery disabled — no provider key configured".
- **Gap** — the green/degraded signal is derived from `email.enabled`
  (key present?), NOT from a real send. And there is no per-event Telegram feed:
  the bot only reflects component status, never "bond #N created".

## Design

### A. Email liveness = "a real send happened recently" (reqs 1 & 2)

**Single source of truth: `email_log`.** Every successful provider acceptance —
event email *or* heartbeat — already lands here with a non-null `ses_message_id`.
Liveness is `now − MAX(sent_at where ses_message_id IS NOT NULL)`.

- **Heartbeat (`backend/heartbeat.mjs`)** — an interval timer (default 6 h,
  `BOND_HEARTBEAT_INTERVAL_MS`) calls `sendEmail(HEARTBEAT_TO, …)`; on a truthy
  message-id it writes an `email_log` row with `event_type='__heartbeat__'`.
  Guarded by `emailEnabled()` (no provider → no attempt → liveness ages out →
  stays degraded, which is the truth). Recipient `BOND_HEARTBEAT_TO`
  (default `bond-heartbeat@futarchy.ai`, a routable address that can be dropped
  or labelled — the liveness proof is *provider acceptance*, the message-id).
- **Health** — `/api/notify/health` `email` grows from `{enabled}` to
  `{enabled, provider, lastSendAgeSeconds, lastHeartbeatAgeSeconds,
  freshnessThresholdSeconds}` (threshold default 8 h = `28800`).
- **Checker `bondEmailComponent`** — new ladder:
  - health unreachable → **outage**
  - `!enabled` → **degraded** ("no provider configured")
  - enabled but `lastSendAgeSeconds == null || > freshnessThreshold` →
    **outage** ("no email sent in N h — delivery may be broken"). *This is the
    new catch: configured-but-silent is no longer green.*
  - enabled + a send within the window + notify cursor not stalled →
    **operational** ("last email sent N min ago").

Because the heartbeat sends every 6 h < 8 h window, a quiet period (zero organic
event emails) still keeps the signal honestly green via the heartbeat — and the
instant real sends stop, it goes red within the window.

> Note: provider acceptance ≠ inbox delivery. Acceptance (a returned message-id)
> is the bar the owner set ("we actually have sent an email"). A future upgrade
> can close the loop by IMAP-polling the heartbeat mailbox for receipt; designed
> for but not required now.

### B. Notification outbox = no silent failure (req 3)

**New append-only table `notify_events`** (the canonical "notification index"),
written by the watcher for every notifiable on-chain event, *independent of*
whether any email/Telegram send later succeeds:

```
notify_events(
  seq        INTEGER PRIMARY KEY AUTOINCREMENT,  -- the "index of the last notification"
  chain_id   INTEGER, block_number INTEGER, tx_hash TEXT, log_index INTEGER,
  event_type TEXT, bond_id INTEGER, summary TEXT,
  created_at TEXT DEFAULT (datetime('now')),
  UNIQUE(chain_id, tx_hash, log_index)            -- idempotent: re-scan never double-counts
)
```

- The watcher's `processLogs` writes one row per `EVENT_RECIPIENTS` event
  (BondCreated / Challenged / Ruled… / etc.). Idempotent on `(chain, tx, log)`,
  so re-orgs / re-scans don't duplicate.
- **Health** grows a `notify` block:
  `{ lastSeq, perChain: [{ chainId, lastNotifiedBlock, headBlock, notifyLagBlocks }] }`.
  `notifyLagBlocks = head − lastNotifiedBlock`. (Generalises today's
  `emailLagBlocks`, which only tracked the email cursor.)
- **Checker** gains a `bond_notify` component: degraded if `notifyLagBlocks`
  exceeds the gap threshold on any chain (the notifier is falling behind the
  chain) — the explicit "last notification within the last X blocks?" guarantee.

This makes both stalls visible: (i) the cursor not advancing (notifier wedged),
(ii) a delivery channel failing (a failed send is *recorded*, not dropped).

### C. Per-event Telegram feed (req 4) — pull model

Keep Telegram credentials where they already live (the bot), keep the backend
channel-agnostic. **Backend exposes a read-only feed; the bot pulls it.**

- **Backend** — `GET /api/notify/events?since=<seq>&limit=<n>` returns
  `notify_events` rows with `seq > since` (newest cursor included), each with a
  human summary + explorer link fields. No auth (read-only, same as `/health`).
- **Bot** — each 15-min tick, after the status check, pulls
  `events?since=<state.lastEventSeq>`, posts one Telegram message per new event
  ("🆕 Bond #12 created on Ethereum", "⚔️ Bond #12 challenged", "⚖️ New judge …"),
  advances `state.lastEventSeq`. Mainnet-only by default
  (`EVENT_FEED_CHAINS=1`) so Sepolia staging noise stays out of the public
  channel; configurable.
- **Gap/liveness alarm** — the bot also reads `health.notify.lastSeq`; if the
  feed is unreachable, or `lastSeq` advances but the bot can't fetch, it posts a
  one-shot "⚠️ notification feed stalled" (no silent failure on the Telegram
  side either).

"New judges": judge registration is an off-chain `judge_profiles` insert (and/or
a JudgeProfileRegistry event). The feed includes judge-profile creations as
`event_type='JudgeRegistered'` rows so they surface alongside bond events.

---

## Why these choices

- **`email_log` as the liveness source** — no new table, and it already unifies
  organic + heartbeat sends, which is exactly the owner's "real or heartbeat".
- **Pull feed over backend-pushes-Telegram** — no secret migration (bot keeps the
  token), backend stays channel-agnostic, the bot already owns a 15-min loop +
  state cursor. 15-min latency is fine for these notifications.
- **Append-only `notify_events`** — gives a true monotonic "index" and a clean
  `since=` cursor with idempotent dedup; decouples "what to notify" from "did a
  channel deliver", which is what makes silent failure impossible.

## Plan (phased)

- **P1 — backend foundation (safe, pure, fully unit-tested):** `notify_events`
  table + `recordNotifyEvent`/`getNotifyEventsSince`/`notifyStatus`/
  `emailDeliveryStatus` in db.mjs; watcher writes outbox rows;
  `backend/heartbeat.mjs`; `/api/notify/health` `email`+`notify` blocks. Tests.
- **P2 — checker semantics:** `bondEmailComponent` green⟺recent real send;
  new `bond_notify` component. Unit tests on the pure builders.
- **P3 — Telegram event feed:** `/api/notify/events` endpoint; bot pulls + posts
  + tracks `lastEventSeq` + gap alarm. Tests against a fake feed.
- **P4 — go-live (gated on the provider credential, parked on owner):** drop
  SMTP/Resend creds in the secrets file → heartbeat sends → `bond_email` greens
  on a *proven* send; live-verify `curl status` shows operational and a real
  message lands; deploy bot + backend; watch one heartbeat cycle.

P1–P3 ship behind the existing no-op mailer (no external side effects until a
credential exists); P4 is the only step that needs the owner's one parked
decision (Google Workspace app password — no new vendor — or a Resend key).
