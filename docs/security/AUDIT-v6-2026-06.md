# SimpleBond v0.6 — Security Audit (contracts + UI)

**Date:** 2026-06-08 · **Method:** 8-dimension review, all analysis on **Codex** agents (codex:codex-rescue + direct `codex exec`), each dimension independently verified; two crux findings re-verified by hand against the live code. **Scope:** `contracts/core/SimpleBondV6.sol`, `contracts/judges/ManualJudgeV6.sol`, profile registries, `OfficialBondDirectory.sol`; `frontend/index.html` + helper modules. **Out of scope:** the indexer backend service, deep economic/MEV modeling, gas fuzzing, formal verification.

> The v6 contracts are **live on mainnet and immutable** — contract findings are mitigated only by (a) operational discipline, (b) UI/indexer guards, or (c) the planned **v7 migration**, which already fixes the two worst contract issues (C1 = H1, C2 = M2). The frontend findings **are** patchable and are the actionable quick wins.

## Remediation status (2026-06-09)
- **H1** — confirmed **intentional**; documented in `SimpleBondV6.sol:challenge()` (the lifetime cap bounds the append-only array + the `claimRefunds` scan; v7 gates on `pendingCount`). No code change.
- **H2 (XSS)** — **FIXED.** `addressLink()` now only links a valid `ethers` address and escapes the `href`/`title`; `rowFromIndexerBond()` coerces `bondId`→number, validates `claimHash` as 0x+64hex, parses amounts defensively; the judge-judged list coerces ids. (Other potential sinks audited: challenge `content` isn't rendered; hash fields are on-chain/fixed; `settleReason` maps to fixed labels.)
- **H3 (claim-hash)** — **FIXED.** New pure helper `frontend/claim-verify.js`; the detail view verifies displayed claim text against the on-chain `claimHash` and, on mismatch, shows a warning and suppresses the challenge action **and** both the bond-level *and per-challenge* judge actions.
- **H4 (USDS approval)** — **FIXED.** `doSusdsDeposit()` now fails closed unless `tokenAddr === MAINNET_SUSDS`, so real USDS can never be approved to a symbol-matched fake token.
- Coverage: unit (`claimVerify`), e2e (`security-hardening.spec.js`: mismatch warning + Browse XSS), and both-mirror surface assertions. The remaining Medium/Low items are unchanged (see below).

## Executive summary
No critical "anyone drains the contract" bug and no exploitable reentrancy drain were found; the judge is operator-gated and trusted, and with the well-behaved approved sUSDS token the core accounting is sound. The most serious issue is an **integrity/censorship flaw**: a poster can permanently exhaust a bond's challenge slots (the cap counts lifetime challenges, not pending), then modify the claim into an **unchallengeable** state — undermining the core "truth bond" guarantee (H1; v7 fixes this). On the UI side, the app **over-trusts the off-chain indexer**: indexer strings reach the DOM partly unescaped (XSS, H2), and displayed claim text is never checked against the on-chain `claimHash` (H3), so a malicious/compromised indexer can mislead users or hijack wallet flows. A create-flow footgun lets a fake "sUSDS" token receive a real USDS approval (H4).

## High findings — detail

### H1 — Lifetime challenge-cap lets a poster make a claim unchallengeable  *(verified by hand; multiply-confirmed)*
- **Location:** `contracts/core/SimpleBondV6.sol:challenge` L266 (`require(challenges[bondId].length < b.maxChallenges)`), `concede` L462-475, `modifyClaim` L482-495.
- **Why:** the cap counts the **append-only lifetime array**, not `pendingCount`. Resolved/conceded/rejected challenges never free a slot. `modifyClaim` only requires `pendingCount == 0`.
- **Exploit:** poster creates a bond with `maxChallenges = N`; self/colluding-challenges N times; **concedes** each (refunds itself, `pendingCount → 0`); calls `modifyClaim` to publish the real claim; every honest `challenge()` now reverts `"Max challenges reached"`. Poster can then close + `withdrawBond`. The public claim is effectively immune to challenge.
- **Impact:** defeats the core "truth bond" guarantee — no funds stolen from third parties, but the mechanism's integrity is broken.
- **Fix:** gate on live capacity: `require(b.pendingCount < b.maxChallenges)` (this is exactly what **v7** does). For live v6: operational mitigation is limited; the strongest answer is the v7 migration. Consider also forbidding poster self-challenges.

### H2 — Indexer-controlled fields reach the DOM unescaped (XSS)  *(triple-confirmed across dimensions)*
- **Location:** `frontend/index.html:addressLink/575-578` (interpolates `addr` into `href` and `title=` unescaped), `rowFromIndexerBond/1980-1997` (no validation of `bondId`/`poster`/`judge`/`claimHash`), rendered via `innerHTML` in Browse (`2198`, `2211-2225`), detail paint (`3757-3766`, `4211`), and the judge "bonds judged" list (`4524-4526`).
- **Impact:** a malicious or compromised indexer (the app's `notifyApiBase` origin) executes JavaScript in the SimpleBond origin → can rewrite displayed tx intent, swap approval spenders, and phish wallet actions.
- **Fix:** validate IDs as integers, addresses via `ethers.getAddress()`, hashes as fixed-length hex; escape attribute values; URL-encode explorer path components; prefer DOM construction over HTML strings; add a strict CSP.

### H3 — Claim text never verified against the on-chain `claimHash`  *(confirmed in 2 dimensions)*
- **Location:** `frontend/index.html:3731-3740` (carries indexer `claimContent` as `claimHint`), `3833-3834`/`3975-3983` (RPC enrich preserves it without hashing), `doChallenge/4252-4282`, `doRule/4443-4447`.
- **Impact:** a challenger escrows against — or a judge rules on — claim text that may differ from the actual on-chain claim; the tx targets the real bond/version while the user read forged/stale text.
- **Fix:** compute `keccak256(toUtf8Bytes(claimContent))` client-side and compare to live `b.claimHash`; hide challenge/rule controls and show a mismatch warning when they differ.

### H4 — Create flow approves real USDS to a fake "sUSDS" token  *(verified by hand)*
- **Location:** `frontend/index.html:renderFundingCard/850-855` (`isSusds = tokenAddr===MAINNET_SUSDS || /USDS/i.test(tokenSym)`), `doSusdsDeposit/957-979` (`usds.approve(tokenAddr, amount)` then `deposit()`), wired from `submitCreate/3343-3353`.
- **Impact:** with the advanced token-override, any token whose **symbol** matches `/USDS/i` is treated as the sUSDS vault; the one-click deposit then approves **real MAINNET_USDS** to that arbitrary address. A poster social-engineered into using a fake "sUSDS" token approves (and loses) the bond amount of real USDS. Bounded to the bond amount (exact approval), not infinite.
- **Fix:** enable the one-click USDS→sUSDS deposit **only** when `tokenAddr` equals the configured/allowlisted sUSDS vault; verify ERC-4626 `asset() == USDS` before approving; fail closed.

## Medium findings — detail (condensed)
- **M1 — fee-on-transfer/rebasing undercollateralization** (`SimpleBondV6` escrow/payout sites; `ManualJudgeV6.validateBond` only checks `active`): nominal amounts recorded without a balance-delta check → undercollateralized/stuck payouts for non-exact tokens. **Mitigated in practice** only because the intended token (sUSDS) is exact-transfer; `createBond` does **not** enforce the directory's approved token. **Fix:** allowlist exact-transfer tokens, or credit `balanceAfter-balanceBefore`.
- **M2 — failed-refund wedge** (`claimRefunds/440-457`): shared cursor advances only after the loop; one reverting `safeTransfer` (blacklisted/malicious recipient) blocks every later pending refund. **v7's pull-payment credits (C2) fixes this.** **Fix (v6):** per-recipient pull credits / skip-on-failure.
- **M3 — RPC quorum:1** (`readProvider/1107-1139`): a single public RPC controls bond struct, `b.judge`, `operator()`, amounts that feed approvals + judge calls. **Fix:** quorum ≥ 2; re-read write-critical fields via the wallet provider before submitting.
- **M4 — indexer rows treated as definitive** (`2013-2041`, `1980-1997`): indexer can censor bonds or fake status/amounts/settleReason. **Fix:** treat indexer as preview; verify visible status/amounts vs chain.
- **M5 — ethers via CDN, no SRI/CSP** (`index.html:7`): CDN/package compromise runs arbitrary JS controlling tx params. **Fix:** self-host pinned ethers or add SRI + `script-src` CSP.
- **M6 — no minimum ruling window** (`createBond/176-178`): `rulingBuffer > 0` is the only check; a ~1s window means no block exists for the judge to rule → `claimTimeout` settles for the poster. **Fix:** enforce protocol minimums (or reject unsafe windows in judge/profile validation).
- **M7 — non-sUSDS amounts shown as "$"** (USD/sUSDS copy + 1:1 rate fallback): a token override displays "3 tokens" as "$3". **Fix:** restrict main UI to the approved token or label non-approved amounts in token units.

## Low / Info
- **L1** `claimRefunds` reentrancy regresses `refundCursor` (no double-spend — status set before transfer); update cursor monotonically / add `nonReentrant`.
- **L2** `claimRefunds` doesn't decrement `pendingCount` → stale invariant (no settlement path relies on it; can mislead indexers/UI).
- **L3** `JudgeProfileRegistryV6.registerProfile` is permissionless and `createBond` checks only `profileJudge == judge` (never `OfficialBondDirectory`) → a bond can use an attacker judge or pin misleading terms to a real judge; enforce directory/owner authorization or make the trust boundary explicit in UI/indexer filtering.
- **L4** `OfficialBondDirectory` admin transfer/pause is admin-callable with no owner-only override → a malicious admin can retain curation; make admin transfer/revoke owner-only.
- **L5** `concede (<= T0)` and `rule (>= T0)` overlap at exactly T0 → ordering decides outcome; make the windows half-open.
- **L6** notify `/status` is enumerable cross-origin without a signature (wildcard CORS) → subscription + masked-email enumeration; require signed/same-origin status queries.
- **L7** 2 `target=_blank` links (`3412`, `4282`) miss `rel=noopener noreferrer`.

## Coverage & residual risk
**Reviewed:** all v6 core/judge/registry/directory contracts and the full frontend (XSS, RPC/secret, wallet/tx, client-trust). **NOT reviewed:** the indexer **backend** service code itself (which several UI findings assume is the trust root — it deserves its own audit), deep economic/MEV/game-theory of the judge incentives, gas fuzzing of `claimRefunds` at large `maxChallenges`, and formal verification of the settlement invariants.

**Prioritized next steps**
1. **Frontend (patchable now):** H2 (escape `addressLink` attrs + validate indexer fields + CSP), H3 (claim-hash check), H4 (gate one-click deposit to the allowlisted vault) — high value, low effort.
2. **Operational (live v6):** only ever use the approved sUSDS token (sidesteps M1); set sane `acceptanceDelay`/`rulingBuffer` defaults in the create UI and warn on tiny windows (M6); raise RPC quorum (M3).
3. **Strategic:** the v7 migration already fixes H1 (pending-cap) and M2 (pull-payment credits) — the two worst contract issues. Audit the indexer backend separately.
