**Date:** 2026-06-09 · **Subject:** `contracts/core/SimpleBondV7.sol` (the new core, Sepolia staging `0xb314Db5C3e049911631B49F37078d2D2BBa4D78c`, candidate for mainnet) plus its reused v6 periphery (`ManualJudgeV6`, `JudgeProfileRegistryV6`, `OfficialBondDirectory`), the v7 cutover surface in the frontend/indexer, and `scripts/v7/deploySimpleBondV7.js`.

**Method:** primary line-by-line hand audit of all 633 lines of `SimpleBondV7.sol` by the session's main model (claude-fable-5), with every payout path's token conservation derived by hand and the v6 baseline diffed function-by-function; a 9-lens multi-agent sweep (accounting, adversarial game-theory, v6→v7 diff, judge integration, frontend, cutover readiness, backend, tests/deploy, timeout semantics — each finding adversarially verified by 3 independent lenses) runs as a breadth cross-check and its confirmed-novel findings are appended in §6 when adjudicated.

**Relationship to the v6 audit:** `AUDIT-v6-2026-06.md` findings are *not* re-reported. Exception: v6 contract findings **inherited** by v7 are listed here, because v7 is not yet deployed to mainnet — inherited flaws are still fixable.

## 1. Verified sound (hand-derived)

- **Token conservation on every path.** createBond/challenge escrow vs. `ruleForPoster` (inline judge-fee push + poster credit = `challengeAmount`), `ruleForChallenger` (fee + winner credit `bondAmount + challengeAmount − fee` + loser sweep of `challengeAmount` each = `bondAmount + (k+1)·challengeAmount`), `rejectChallenge`, `rejectBond`, `withdrawBond`, `claimTimeout`, `concede` — all conserve exactly for exact-transfer tokens. No path strands value; no path over-credits.
- **`pendingIds`/`pendingPos`/`pendingCount` triple-invariant** holds at every mutation site (`challenge`, all four resolution paths, both sweeps). Swap-and-pop (`_removePending`) is correct including the challengeIndex-0 edge (1-based position sentinel avoids the 0-collision). The winner is removed from the live set **before** the loser sweep (`ruleForChallenger`), so no double-credit is possible. Sweeps are effects-only and bounded by `pendingCount ≤ maxChallenges ≤ MAX_CHALLENGES_CEILING = 100` — the v6 settle-gas-bomb class is closed (C1/C2 as designed).
- **`claim()` is strict CEI + OZ `nonReentrant`** (read → require → zero ledger → emit → transfer). Credits keyed `[recipient][token]` quarantine a misbehaving token: a shortfall in token X can never block or contaminate sUSDS claims.
- **ManualJudgeV6 ↔ v7 integration is clean.** Forwarded signatures (`ruleForPoster/ruleForChallenger/rejectChallenge/rejectBond` with `(bondId, i, feeCharged, content)` / `(bondId, content)`) are byte-identical to v7's; the judge holds no per-bond state; v7's inline fee push lands as plain ERC-20 balance withdrawable via `withdrawFees`. Serving v6 and v7 concurrently only commingles fee balances (operator-trusted).
- **Cutover surface already exists.** v6 and v7 `Bond` structs are field-for-field identical (same order, no removed/added fields), so `bonds()` destructuring is version-safe; the frontend has `credits()` reads, a claimable-credits banner, and `claim(token)` writes; the backend ABI covers `Credited`/`Claimed` and re-snapshots on `Credited`.

## 3. Residual risk (no action forced; documented)

- **`claimTimeout` cross-challenge semantics are inherited verbatim from v6** (v6:438-449 ≡ v7:575-591): timing out any one pending challenge settles the *whole* bond in the poster's favor, refunding all other pending challengers even if their ruling windows are still open. Judge-liveness-bounded: the judge can always defuse by ruling/`rejectChallenge`-ing within each window — the same operational requirement v6 already runs under. A poster sock-puppet challenge opens a poster-favoring timeout clock; each judge rejection both refunds it and frees pending capacity, and any refile starts a *later* clock.
- **H1 residual under C1:** a poster can still blockade honest challenges by keeping the pending set full of self-challenges (atomic `concede×N → modifyClaim → refile×N`), but unlike v6 this requires continuous, publicly-visible maintenance, locks `N·challengeAmount`, and every judge `rejectChallenge` frees a slot the poster must race to refill. Design-inherent to any pending-cap; materially better than v6's free permanent lockout.
- **Trust-model dependencies unchanged from v6:** judge = operator-gated vetted contract; profile registry is permissionless (v6-L3) with the official directory + UI as the curation layer; directory admin governance (v6-L4) now also gates *new-bond token approval* (see V7-1 fix) — a hostile directory admin could block new bond creation (existing bonds unaffected: `challenge`/payout paths never re-check the directory).
